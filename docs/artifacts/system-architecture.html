COFFWE System Architecture

Every layer the finished estate ecosystem needs, what flows between them, and the realistic tool options at each level — so the small choices land in the right context.

The loop

The thing that makes this a digital twin rather than a dashboard is the return path: decisions made by the AI brains flow back into the simulated estate and change it. Everything else exists to make that loop trustworthy.

Tools at each level

"Pick" is what I'd choose for this project and why; "also exists" is what you'd meet in industry doing the same job — worth recognizing by name even when we don't use it.

01

Simulation engine

Phase 2

Generates the estate's ground truth: weather, soil moisture, plant growth, pest pressure, worker activity, machine wear.

PickCustom Python + NumPy/SciPy, with SimPy if we need event scheduling
Also existsMesa (agent-based modeling), AnyLogic/Simulink (commercial), pure discrete-event frameworks

Writing the agronomy math by hand is the statistics learning — a framework would hide exactly the part worth understanding.

02

Virtual devices

Phase 3

Fake sensors and actuators that behave like real field hardware — including dropouts, drift, and late readings.

PickPython paho-mqtt publishers, one process per device group
Also existsHTTP POST, gRPC streaming, CoAP, LoRaWAN simulators, Node-RED

MQTT is the genuine IoT protocol — teaches QoS levels, retained messages, and last-will handling you'd need with real hardware.

03

Message broker

Phase 3

Decouples device publishing from consumer reading, so neither side blocks the other.

PickMosquitto locally → bridged to GCP Pub/Sub (always-free tier)
Also existsEMQX, HiveMQ, Kafka / Redpanda, NATS, RabbitMQ, Redis Streams

Mosquitto is tiny and free; the Pub/Sub bridge is where managed cloud messaging gets learned without a bill.

04

Ingestion & pipelines

Phase 3

Subscribes, validates, normalizes, and writes; later runs scheduled batch jobs (daily rollups, retraining data).

PickPython asyncio consumer + Pydantic validation; Prefect for scheduled jobs
Also existsApache Beam/Dataflow, Airflow, Dagster, dbt (transforms), Benthos, Telegraf

Hand-writing the consumer first shows you what the managed tools are abstracting — then Airflow/Dagster make sense rather than feeling magic.

05a

Relational store

Phase 1 — now

The estate's structure: blocks, 44,950 tagged plants, workers, machines, inventory, harvest batches.

PickPostgreSQL (native, via Homebrew) + SQLAlchemy 2.0
Also existsMySQL, SQLite, CockroachDB; SQLModel or Django ORM instead of SQLAlchemy

Already decided. Postgres also carries us into time-series and vector search later, so one engine covers three jobs.

05b

Schema migrations

Phase 1 — pending

Versioned, reviewable schema changes instead of dropping and recreating tables.

PickAlembic (pairs natively with SQLAlchemy)
Also existsFlyway, Liquibase, sqitch, yoyo, Prisma Migrate, Django migrations

This is the open question — see "decisions due" below.

05c

Time-series store

Phase 3

Every sensor reading from every device, forever — the volume side of the data problem.

PickTimescaleDB extension on the same Postgres
Also existsInfluxDB, ClickHouse, Prometheus (metrics only), BigQuery, DuckDB (local analytics)

One database engine to run and back up, but you still learn real hypertables, retention policies, and continuous aggregates.

05d

Object & analytics

Phase 4+

Camera-trap images, model artifacts, raw data archives, and heavy analytical queries.

PickGCS free tier for objects; BigQuery sandbox or DuckDB for analytics
Also existsMinIO (self-hosted S3), S3, Snowflake, Redshift

BigQuery's sandbox is genuinely free with no card charge; DuckDB costs nothing and runs locally — both are worth knowing.

06

Digital twin core

Phase 4

Holds the authoritative current state, its history, and the ability to answer "what if" without touching reality.

PickCustom FastAPI service over Postgres (+ Redis for hot state later)
Also existsEclipse Ditto (open-source twin platform), Azure Digital Twins, AWS IoT TwinMaker

The managed platforms hide state reconciliation and drift detection — which is precisely the digital-twin concept you're here to learn.

07

ML & statistics

Phase 6

Forecasting yield and weather, predicting rust/borer outbreaks, detecting faulty sensors, optimizing schedules.

Pickscikit-learn + statsmodels first, XGBoost/LightGBM for tabular, PyTorch only when DL earns it; MLflow for tracking; Colab free GPU
Also existsProphet, Darts, PyMC (Bayesian), Optuna (tuning), OR-Tools (scheduling), Vertex AI, Weights & Biases

Classical models first means you can tell whether deep learning actually helped — otherwise every result looks like magic.

08

AI brains & orchestration

Phase 7

Each brain reasons over its domain; the supervisor resolves conflicts between them and decides what reaches you.

PickClaude Agent SDK / tool-use loops + a custom supervisor; pgvector for retrieval
Also existsLangGraph, CrewAI, AutoGen, LlamaIndex; Chroma/Qdrant/Pinecone for vectors

A hand-built supervisor keeps the escalation policy explicit and inspectable — which matters more here than framework convenience.

08b

Guardrails & evaluation

Phase 7

The thresholds that separate "the agent just does it" from "ask Raja first" — and the harness proving the agents behave.

PickExplicit policy rules in code + a custom eval harness with LLM-as-judge
Also existsOPA/Rego, Guardrails AI, Ragas, DeepEval, promptfoo

Your guardrail thresholds are project decisions, not library config — they belong somewhere you can read them in one sitting.

09

Actions & workflows

Phase 8

Turns a decision into an actuator command or a worker task, then confirms it actually happened.

PickCelery or RQ on Redis to start; Temporal if we want durable retry/compensation
Also existsPrefect flows, APScheduler, GCP Cloud Tasks, AWS Step Functions

Verification is the hard half: a command sent is not work done, and the twin must reflect reality either way.

10

Presentation

Phase 4, then 8

The estate map, live readings, alerts, and the approval inbox where you accept or reject critical calls.

PickStreamlit for the first dashboard; FastAPI + React later when interactivity demands it; Grafana for ops metrics
Also existsPlotly Dash, Panel, Gradio, Next.js, Observable

Streamlit gets a working dashboard in pure Python in an afternoon — the UI shouldn't block the systems learning this early.

11

Platform & ops

Phase 9–10

Containers, infrastructure as code, CI/CD, deployment, observability, secrets, and cost control.

PickDocker, Terraform, GitHub Actions, Cloud Run + e2-micro (always-free), Cloud Logging + OpenTelemetry, Secret Manager
Also existsPulumi, Ansible, GitLab CI, Kubernetes/GKE, Prometheus + Grafana, Vault, SOPS

Docker arrives here, not now — containerizing is much clearer once there are several real services that need to ship together.

12

Testing & data quality

Throughout

Proving the simulator's invariants hold, the pipelines don't silently corrupt, and the models haven't drifted.

Pickpytest + Hypothesis (property-based testing), Pandera for dataframe contracts, Evidently for drift
Also existsGreat Expectations, Locust (load), Soda, dbt tests, Testcontainers

Property-based testing fits simulations unusually well: you assert laws ("soil moisture never exceeds saturation") instead of fixed examples.

Decisions due now

Settled

  • Python end-to-end, GCP always-free tier, native Postgres via Homebrew for this phase.
  • Docker deferred to Phase 9 — one new concept at a time, and containers make more sense once several services exist.

Open — the one I need from you

  • Alembic now, or plain create_all() first? Alembic means every schema change from today onward is a reviewable migration file — the professional habit, and genuinely useful once the schema starts evolving in Phase 2. The cost is a little extra setup today while the schema is still moving fast.

Deliberately deferred

  • Time-series engine (Phase 3), twin service shape (Phase 4), agent framework (Phase 7), deployment target (Phase 9) — each is easier to choose with the previous layer actually built.
A map, not a contract — any layer can be revisited when the one before it teaches us something new.
